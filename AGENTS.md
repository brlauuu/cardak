# Repo conventions

cardak is a project-centric deck for WezTerm panes and Claude Code sessions: it groups
every pane by project, jumps to a pane on click, sets a color scheme per project, shows
agent status (working / waiting / idle), and attributes CPU/RAM to the pane that caused it.
`PLAN.md` is the spec; read it before starting on a milestone.

## Stack
- **Python 3.13**, managed with **uv** (`uv run`, `uv add`; never pip into the system).
- **Textual** for the TUI, served in a browser via `textual-serve`.
- **psutil** for processes, **SQLite** for storage, TOML config at `~/.config/cardak/projects.toml`:
  read with `tomllib`, new projects appended with `tomli-w`, existing keys edited in place with
  **`tomlkit`** (keeps comments and layout).
- **WezTerm** is the only supported terminal (`wezterm cli` plus a generated Lua module).
- Developed and tested on Kubuntu 24.04, KDE Plasma 5.27 on **X11**, WezTerm 20240203.

## Layout
```
pyproject.toml
src/cardak/
  cli.py                  # cardak [tui] | hook | summarize | hooks … | wezterm install | themes …
  core/{config, resolver, snapshot, source, filter, navigate, themes}.py
  core/{agents, store, alerts, focus, hook}.py         # M4: agent status
  core/{summary, summarize}.py                         # #30: waiting summaries
  core/{accounting, resources, recent}.py              # M5: resources
  collectors/{wezterm, processes, claude, hooks, transcripts, machine, docker}.py
  ui/{app, widgets, theme_picker, detail}.py
  wezterm/{cardak.lua, generate.py, install.py, schemes.py, files.py, tint.zsh}
  claude/install.py       # M4: cardak's hooks in ~/.claude/settings.json
  llm/anthropic.py        # #30: the Anthropic summarizer (SDK imported lazily)
  sounds/*.wav            # generated by scripts/make_sounds.py
skills/{checkpoint,where-were-we}/SKILL.md
spikes/                   # M0 throwaway scripts (PEP 723 inline deps: `uv run spikes/x.py`)
tests/                    # mirrors src/cardak; fixtures/ holds sanitized recordings
```

## Code
- Small, single-purpose modules.
- **Layering:** `cli → {ui, wezterm, claude, llm} → core → collectors`. `core` never imports
  `ui`, `cardak.wezterm`, `cardak.claude` or `cardak.llm`, `collectors` import nothing from
  cardak, and `wezterm/` (the Lua module and its installer), `claude/` (the hooks installer)
  and `llm/` (model providers for waiting summaries) import nothing from cardak. `core`
  defines the `Summarizer` protocol; `cli.py` hands it a provider. `core/filter.py` is core's only
  Textual import (`textual.fuzzy`). `cli.py` is the only module at the
  package root besides `__init__.py`; anything else at that level makes `src/cardak`
  and its subpackages import each other (a directory-level cycle enola reports).
- **One interface per external format.** All WezTerm invocation and parsing lives in
  `collectors/wezterm.py`; all Claude Code parsing lives in `collectors/claude.py`
  (session files), `collectors/hooks.py` (hook payloads) and `collectors/transcripts.py`.
  Nothing else touches raw `wezterm cli` output or reads files under `~/.claude/`; the one
  writer there is `claude/install.py`. Neither format is a stable API.
- Read-only by default: the deck observes and focuses panes; it does not launch or drive agents.
- Never edit `~/.config/wezterm/wezterm.lua`, `~/.claude/settings.json` or anything else
  under `~/.config` or `~/.claude` without asking. Generated files go to a path the user
  `require`s or opts into.

## Tests
- **pytest**, tests in `tests/`, mirroring `src/cardak/`.
- Parsers are tested against **recorded fixtures** in `tests/fixtures/`, never against the
  live machine. When a format surprises you, record it as a new fixture first, then fix.
  `spikes/out/wezterm_cli_list.json` is the first one.
- CI (from M1) runs `ruff check`, `ruff format --check`, `pyright` and
  `pytest --cov --cov-branch --cov-fail-under=80`. Don't lower the floor to get green;
  cover the code or explain the exclusion here.

## WezTerm (measured in M0, see PLAN §4)
- **Always call `wezterm cli --no-auto-start`.** Without it, a `wezterm cli` call with no
  GUI running silently spawns a headless `wezterm-mux-server`, which then shadows the
  real GUI for later calls.
- **Outside a WezTerm pane, `wezterm cli` does not find the GUI.** It only tries the mux
  socket `$XDG_RUNTIME_DIR/wezterm/sock`. Set `WEZTERM_UNIX_SOCKET` to the GUI's
  `gui-sock-<pid>` in the same directory, and re-resolve after a connection failure (the
  pid changes when the GUI restarts). Inside a pane the variable is already set.
- **Jumping** (`core/navigate.py`): `activate-pane` selects the pane but does not raise
  its window, so the deck then writes `OSC 1337 SetUserVar=cardak_focus=base64(<pane_id>:<nonce>)`
  to its **own** `/dev/tty`, and `cardak.lua` (shipped in `src/cardak/wezterm/`) raises the
  target window. It never writes to another pane's tty. KWin allows the raise because the
  request comes from the focused WezTerm window (verified live in M2). From anywhere else
  (the browser front-end, M7), use the EWMH `_NET_ACTIVE_WINDOW` request with source=2
  (`spikes/02_activate_pane.py --fallback`).
- `cardak wezterm install` installs `cardak.lua` (only over a file starting with
  `-- cardak: generated`, else `--force`); users add `require('cardak').apply(config)` to
  `wezterm.lua` themselves. cardak never reads or edits `wezterm.lua`.
- **Textual gotchas (M2):** `AUTO_FOCUS` focuses the first focusable widget in compose
  order even when it is hidden, so the deck focuses its tree explicitly on mount; and
  `Tree.clear()` leaves the cursor on no line, so a rebuild without a target puts it on row 0.
- The X11 window title is the **active pane's title**; `set-window-title` does not change it.
- `cwd` in `wezterm cli list` comes from OSC 7, so it follows the shell, not the foreground
  process. Fallback when it is missing: `/proc/<pid>/cwd`.

## Themes (M3)
- Files cardak writes (all atomic, through symlinks, mode kept; never over a file whose first
  line lacks cardak's marker, except a CLI command given `--force`; only when content changes):

  | Path | Written by | Content |
  |---|---|---|
  | `~/.config/wezterm/cardak.lua` | `cardak wezterm install` | static module: focus, theming, preview |
  | `~/.config/wezterm/cardak_projects.lua` | deck on every config change; `cardak themes apply` | project path → scheme (only when cardak.lua is installed there) |
  | `~/.config/cardak/tints` | same | `path<TAB>#rrggbb` for the zsh hook |
  | `~/.config/cardak/tint.zsh` | `cardak themes zsh` | the opt-in per-pane tint hook |
  | `~/.config/cardak/anthropic_key` | the user (cardak only reads it, in `cardak summarize`; refused with group/other bits) | the Anthropic API key for waiting summaries |
  | `~/.cache/cardak/schemes-<wezterm version>.json` | scheme probe | built-in schemes and their colors |
  | `~/.local/state/cardak/cardak.db` | `cardak hook`; the deck (`seen_at`); `cardak summarize` (`summaries`) | agent sessions and raw hook events (7 days); waiting summaries with their cost or error (62 days) |
  | `~/.local/state/cardak/focus` | `cardak.lua` (module 3) | `# cardak-focus: 1`, then the last 64 `<pane_id|none> <unix_ms>` |
  | `~/.local/state/cardak/hook.log` | `cardak hook`, `cardak summarize` | tracebacks; restarted past 1 MB |
  | `~/.claude/settings.json` | `cardak hooks install` / `uninstall` only, after asking (or `--yes`) | cardak's entries only; a `.cardak-backup-<time>` copy first |
- `cardak.lua`'s second line is `-- cardak-module: N`. Bump `MODULE_VERSION`
  (`wezterm/generate.py`) whenever the Lua module gains a feature the Python side relies on;
  the deck and `cardak themes apply` tell users with an older module to re-run
  `cardak wezterm install`.
- The scheme list comes from a headless probe: `wezterm --config-file <probe> ls-fonts`
  evaluates a config that dumps `wezterm.color.get_builtin_schemes()`, without opening a window.
- Preview is keyed by **project path** (`cardak_preview` user var with JSON), lives only in
  WezTerm's Lua state, and is cleared by any config reload, which is also what saving does.
- Live checks with a user WezTerm already running: start the test GUI with
  `--always-new-process`, address it through its own `gui-sock-<pid>`, and capture windows
  filtered by `_NET_WM_PID`, so nothing touches the user's windows.

## Claude Code (measured in M0)
- `~/.claude/sessions/<pid>.json` maps a running `claude` pid to `sessionId`, `cwd`,
  `status` and `name`. It is written **after the first prompt**; before that there is only
  a `<pid>.<hash>.key` file.
- A `claude` process's child tree includes its MCP servers (`npm exec @playwright/...`).
  Don't attribute their CPU/RAM to the agent's work.

## Agent status (M4)
- Claude Code runs `cardak hook` (registered by `cardak hooks install`) on every hook event.
  It parses the payload, applies `core/agents.apply` inside a SQLite `BEGIN IMMEDIATE`
  transaction, and on a transition **into** waiting spawns `notify-send` and a sound
  detached. **It always exits 0 and prints nothing**: stdout can reach the conversation
  and exit code 2 on `PreToolUse` blocks the tool. Failures go to `hook.log`.
- There is no daemon yet: hook processes and the deck share `cardak.db` (WAL, 2 s busy
  timeout). The deck decides "seen" (jump, or ≥ 1 s of focus from the focus history) and
  writes `seen_at`; hooks never do.
- Tests never touch the real state dir: `tests/conftest.py` points `XDG_STATE_HOME` at a
  temp dir for every test.

## Claude Code hooks (measured in M4, Claude Code 2.1.306)
- Fixtures: `tests/fixtures/hooks/` (recorded with `spikes/04_record_hooks.py` and
  `claude --setting-sources project --settings <scratch>`, which leaves the user's settings
  and hooks out). Record a new one before handling a payload that surprises you.
- A hook runs as `sh -c` under the `claude` process and inherits its environment, so
  **`WEZTERM_PANE` reaches the hook**; it is the session → pane join.
- Around an approval: `PreToolUse` → `PermissionRequest` → `Notification`
  (`notification_type: permission_prompt`, "Claude needs your permission") → the user
  answers → `PostToolUse`. Nothing fires on the answer itself.
- `AskUserQuestion` goes `PreToolUse` → `PermissionRequest` (same tool) → `PostToolUse`,
  with no `permission_prompt` notification.
- `Stop` carries `last_assistant_message`. A `SubagentStop` (an internal agent) often
  follows it; ignore it. About 60 s after a `Stop`, `Notification` `idle_prompt` ("Claude is
  waiting for your input") fires.
- `/clear` sends `SessionEnd` (`reason: clear`) and a `SessionStart` (`source: clear`) with a
  **new `session_id`** from the same pane.
- **`cardak hook` budget: < 150 ms.** Claude Code runs it synchronously, 2–3 times per tool
  call. Measured median 87 ms (`.venv/bin/cardak hook` with a `Stop` payload, notifications
  off, load 3.2; bare `python -c pass` is 22 ms). `cli.main` dispatches `hook` before
  argparse, every other command imports what it needs inside its function, `config.py`
  imports the TOML writers where it writes, and `core/hook.py` imports `alerts` only to ping.
  `tests/test_cli.py::test_hook_does_not_import_textual` and `::test_hook_imports_only_what_it_needs`
  guard it (`anthropic`, `cardak.llm` and `core.summary(ize)` stay out, ping path included,
  `::test_pinging_hook_imports_no_summarizer`). Check `python -X importtime -c "import cardak.cli"` after adding imports.
- **`cardak summarize <session_id> <wait_since>`** (#30) is spawned detached by the hook on a
  ping, when `[summary]` is on and `~/.config/cardak/anthropic_key` exists. It is not budgeted
  and may import the SDK; like the hook it prints nothing, exits 0 and logs to `hook.log`.
  It reads the key file only (never `ANTHROPIC_API_KEY`), refuses a key with group/other
  bits, and sends only the current turn: M4's `last_message` belongs to the previous turn
  during a mid-turn wait, so that wait reads this turn's assistant text from the transcript.
  The wait is identified by `status_since`, which equals the `ts` of the event that started it.
- `SessionStart` and `SessionEnd` have no `permission_mode`. In `auto` mode, plain `ls` and
  file writes run with no `PermissionRequest`.
- Sessions driven from a pty did not get `~/.claude/sessions/<pid>.json` or a transcript
  file, so don't rely on either existing. `tests/fixtures/transcripts/basic.jsonl` keeps the
  structure of a real transcript, with its content replaced by neutral text. Lines include
  many non-message types (`attachment`, `api-request*`, `mode`, `ai-title`, `last-prompt`,
  `file-history-*`, `queue-operation`, `system`); user lines with `isMeta` are not prompts.

## Processes (measured in M1)
- **Never use psutil's `Process.terminal()`** in a long-running process: psutil memoizes
  its device → tty map on first use, so panes opened after the deck started have no tty.
  `PsutilTable` reads `tty_nr` from `/proc/<pid>/stat` and rebuilds the map every snapshot.

## Resources (measured in M5, Docker 29, cgroup v2 with the systemd driver)
- All Docker access lives in `collectors/docker.py`, read-only: `GET /containers/json` over the
  unix socket (`DOCKER_HOST=unix://…` honoured) for `Id`, `Names`, `Labels`
  (`com.docker.compose.project.working_dir`) and bind `Mounts`; usage from cgroup files.
  Containers: `/sys/fs/cgroup/system.slice/docker-<full id>.scope/`. BuildKit build steps:
  `/sys/fs/cgroup/system.slice/system.slice:docker:<build id>/`, present only while a step
  runs, readable without the API. Both have `memory.current` and `cpu.stat` (`usage_usec`).
  No Docker or no access: Docker usage silently falls into Other.
- A `docker build` runs under Docker, not in the pane; the pane only holds the client. Builds go
  to the one project with a pane running a build client, else to Other.
- Machine used = `MemTotal − MemAvailable` (`collectors/machine.py`). Pane RAM is RSS, which
  double-counts shared pages, so Other (machine used − Σ projects) is clamped at 0.
- "GB" in `[resources]` keys means GiB. Missing keys are derived from the machine
  (`core/resources.derive`): warn below 15% available, critical below 7% or swap full, a pane or
  project over 25% of RAM or half the cores. Other as a whole is never marked.

## Commits and PRs
- Conventional commits with a scope where it helps: `feat(collectors): ...`,
  `fix(ui): ...`, `docs: ...`, `ci: ...`, `chore: ...`, `release: cut X.Y.Z`. End the subject
  with the issue number when there is one: `(#12)`.
- Work on a branch and open a PR; `main` only moves through merged PRs. `main` is
  protected: the `test` check must pass on an up-to-date branch, no force pushes or
  deletion, and the rule binds admins.

## Versioning and releases
- **The version lives in `pyproject.toml` only.** Nothing else quotes it.
- **`CHANGELOG.md` is the release notes.** Every merged PR adds a line under
  `## Unreleased`, grouped Added / Changed / Fixed, ending with the issue or PR number.
  Write for the person using the deck, not the person reading the diff.
- Release: graduate Unreleased into `## X.Y.Z — YYYY-MM-DD`, bump `pyproject.toml`, open
  `release: cut X.Y.Z` as its own PR, and tag `vX.Y.Z` on `main` only after that PR is
  merged and CI is green. **Minor** for a new user-visible capability, **patch** for fixes,
  dependencies, docs and internal work.
- **Nothing is tagged before there is something to run.** M0 (spikes) shipped untagged;
  the first tag is `v0.1.0`, when the M1 read-only deck works. The version stays 0.x until
  the deck covers M0–M5.

## Architecture checks (enola)
- `.enola/` is gitignored, so the baseline is per-machine and a re-pin does not travel in a PR.
- Re-pin with `enola baseline pin` after a deliberate structural change. A new language
  appearing (the first `.py` / `.lua` files) also makes the old baseline incomparable.
- **M1 re-pinned the baseline** after the review fixes. At the pin: no cycles and no
  complexity findings (M1 moved the core modules into `core/` to break a
  `src/cardak` ↔ `src/cardak/ui` cycle, and split `summarize`, `build_snapshot`,
  `add_project` and `PsutilTable.snapshot`).
- **Four hotspot findings are accepted as design**, reported but not failed:
  `config.load`, `LiveSource._poll`, `LiveSource._reload_if_changed` and
  `DeckApp._rebuild` (fan-in × fan-out 12–25). M2 adds `DeckApp._render` (5 × 3), which
  applies the filter, sets the header and rebuilds: the same kind of coordinator.
  M3 adds three more of the same kind: `config.add_project`, `generate.write_generated` and
  `ThemePickerScreen._refill` (3–4 × 6–8). `exported-surface` (29 of 29) is advisory: Python
  has no export lists, and internal helpers are already `_`-prefixed. Each one coordinates the steps of a
  single operation; splitting it would only move the fan-out somewhere else.
- **M4** split its outliers once: `agents._transition` (21) became one handler per event
  (`HANDLERS`), `cli._hooks` (14) lost `_write_settings`, `DeckApp._rebuild` (14) lost
  `_leaves` and `_empty_label`, and agent views moved into `snapshot._row`. Accepted after
  that round:
  - complexity 10–11 in `read_transcript`, `agents.apply`, `tool_summary`, `detail_text`;
  - `agents._set_status` (fan-in 8: every event handler uses it);
  - coordinators `LiveSource._poll` (3 × 6), `Store.update` (4 × 4) and
    `DeckApp._empty_label` (3 × 5).
- **#30 (waiting summaries)** split `hook.run` (`_ping`), `summarize._inputs`
  (`_turn_text`, `_pending_tool`), `summary.validate` (`_unquoted`) and `detail_text`
  (`_needs`, back to 11). Accepted after that: `config.load` crossing into god-class
  (fan-in 8: the summarizer is one more reader), `read_transcript` (3 × 5) and
  `config_path` (5 × 3) as hotspots, and `core/summary` in `exported-surface`.
- **M5 part 1 (live numbers)** split `docker._container` (14), `accounting._attach_builds` /
  `_attach_containers` and `config._resources`. Accepted after that: `_pane_procs` at
  complexity 10, and the coordinators `LiveSource._resources` (3 × 6) and `widgets.usage`
  (5 × 4: every row kind formats its numbers through it).
- enola's complexity and hotspot detectors flag **relative** outliers: fixing the
  top one promotes the next. Judge a new one by its absolute size, not by its
  being listed.
